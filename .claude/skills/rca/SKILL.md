# RCA 리포트

- 대상: `incident-logs/$ARGUMENTS/` (원본. 읽기만 한다)
- 결과: `docs/rca/$ARGUMENTS.md`
- `$ARGUMENTS` 가 비어 있거나 폴더가 없으면 `ls incident-logs/` 결과를 보여 주고 묻는다.
- 단계마다 결과를 리포트 해당 절에 쓰고, 다음 단계로 넘어간다. 참고 예시: `docs/rca/a-connection-pool.md`

## 1. 수집 범위
- 파일을 통째로 읽지 않는다. `wc -l` · `head` · `tail` · `grep -c` · `grep -n` · `sed -n` · `awk` 집계만 쓴다.
- 파일별 줄 수 · 기록 기간 · 시각 형식 · 타임존을 표로 정리한다. 오프셋 없는 로그는 다른 파일의 같은 사건과 초 단위로 맞춰 타임존을 판정하고, 근거를 적는다. KST 변환 규칙을 표로 남긴다.
- 집계 함정을 적는다: 스택트레이스 연속행(엔트리 기준으로 센다), access 로그 시각 = 요청 종료 시각, 이벤트성 로그의 "기간"은 수집 범위가 아님.
- 분 단위 이상 건수와 평시 수준을 비교해 분석 창(앞 여유를 넉넉히, 뒤는 복귀 확인만큼)을 정한다. 이 절에서는 원인을 다루지 않는다.

## 2. 타임라인
- 분석 창 안의 사실만 시각순으로 쓴다. **모든 줄에 `파일:줄번호`** 를 단다. 해석은 쓰지 않는다.
- 반복 메시지는 첫 발생 줄 하나 + 분 단위 건수로 묶는다. 파일 간 1초 이내 차이는 "(선후 불확실)"로 표시한다.

## 3. 가설
- 판정 없이 가설을 **2개 이상** 먼저 세운다(코드 · DB · 트래픽 · 배포/설정 등 서로 다른 축).
- 가설마다 지지 근거(2절 행 — `파일:줄번호`) · **반증 조건** · **확인 방법**(실행할 명령)을 표로 쓴다.
- 가장 많이 나온 오류는 우선 **증상**으로 분류하고, 가설은 "왜 그 시점부터 그랬는가"를 설명해야 한다.

## 4. 반증과 판정
- 먼저 로그로 반증을 시도한다. 실행한 명령과 출력을 그대로 남기고, 가설별로 유지 / 기각 / 판단 불가(로그 부족)를 적는다.
- 유지된 가설을 코드 · 설정과 대조한다: 로그에 찍힌 설정값 ↔ 설정 파일, 스택의 클래스 · 메서드 ↔ 소스 `파일:줄번호` 인용.
- 최종 판정은 채택 / 기각으로 정리한다. 확인하지 않은 전제는 전제라고 쓴다. 판정과 별개로 보인 이상 동작은 "의심 동작"으로 따로 적고 고치지 않는다.
- DB 확인이 필요하면 읽기 계정 `readonly` 만 쓴다.

## 5. 리포트 작성
다음 절을 이 순서로 쓴다.
1. **요약** — 언제 · 무엇이 · 직접 원인 · 촉발 조건 · 확신 수준(높음/중간/낮음과 이유)
2. **원인** — 채택한 가설의 인과 사슬
3. **근거 로그 줄** — `파일:줄` · 발췌 표. 실제로 `sed -n` 으로 확인한 줄만 넣는다
4. **수정안** — 지금 적용할 변경(파일 · 변경 · 테스트 명령). 제안만 하고 코드는 바꾸지 않는다
5. **재발 방지** — 구조적 장치와 각 장치가 막는 것
6. **모니터링 항목** — 지표 · 임계값 · 이번에 울렸을 시각 · 사용자 영향보다 앞선 시간
7. **확인하지 못한 것** — 항목과 막힌 이유, 다음을 위해 남겨야 할 로그

## 6. 마스킹 후 저장
- 리포트를 저장하기 전에 [masking-rules.md](masking-rules.md) 의 규칙을 적용한다.
- 리포트 맨 끝에 적용 건수 한 줄을 남긴다(예: `마스킹 적용: IP 23건 · 이메일 0건 · ...`).

## 하지 말 것
- 로그에 없는 줄을 인용하지 않는다. 줄번호는 인용 전에 다시 확인한다.
- 가장 많이 나온 오류를 곧바로 원인이라고 부르지 않는다.
- 원본 로그(`incident-logs/`)와 소스 코드를 수정하지 않는다.
- 마스킹 대응표(원본 ↔ 별칭)를 파일로 남기지 않는다.
- 마스킹 전 원본을 임시 폴더에 복사해 두지 않는다.
