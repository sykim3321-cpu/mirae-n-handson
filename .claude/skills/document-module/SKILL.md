# 레거시 모듈 문서화

- 인자: `$ARGUMENTS` — 첫 번째는 모듈 경로(예: `legacy/item-bank-php`), 나머지는 범위 제한(예: `search.php 만`). 범위 제한이 있으면 그 밖은 "범위 밖"으로만 적는다.
- **분석 대상 폴더의 파일은 읽기만 한다.** 수정 · 생성 · 삭제는 `docs/<모듈명>/` 안에서만 한다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 다른 경로면 멈추고 물어본다.
  - `legacy/item-bank-php` → `item-bank` / `legacy/assignment-thymeleaf` → `assignment` / `legacy/grade-mssql` → `grade`
- 산출물: `docs/<모듈명>/ARCHITECTURE.md` · `ERD.md` · `BUSINESS-RULES.md`. 이미 있으면 덮어쓰기 전에 읽고 알린다.

## 절차

단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 저장하지 않은 채 다음 단계를 시작하지 않는다.

0. **계획 먼저 제시** — 모듈명, 읽을 파일 목록(줄 수 포함), 범위 제한, 단계별 산출 파일을 보여 주고 확인을 받은 뒤 시작한다.
1. **진입점** — URL · 화면 · 프로시저 등 외부에서 들어오는 지점을 표로 정리한다(파일:줄번호, 메서드, 파라미터). → `ARCHITECTURE.md` 에 저장.
2. **의존 관계** — 진입점이 부르는 공통 코드 · 외부 라이브러리 · DB 객체(테이블 · 뷰 · 프로시저)를 호출 방향(A → B)으로 적는다. 확인 못 한 것은 "미확인 목록"에 둔다. → `ARCHITECTURE.md` 에 덧붙여 저장.
3. **데이터 흐름** — 입력 → 검증 → SQL → 출력 흐름과, 참조 DB 객체의 ERD(Mermaid `erDiagram`)를 만든다. 스키마 근거는 `db/mariadb/init/` 또는 `db/mssql/init/` 에서 찾는다. 뷰는 정의(WHERE 조건)까지 인용한다. → `ERD.md` 에 저장.
4. **비즈니스 규칙 후보** — 조건문 · SQL 에 있는 것만 규칙으로 올린다. 아래 형식을 따르고, 맨 앞에 "먼저 볼 것"(주석-코드 불일치 · 같은 규칙 다른 구현 · 기능 없음) 표를 둔다. 주석뿐인 내용은 "주석만 있는 내용" 절에 따로 둔다. → `BUSINESS-RULES.md` 에 저장.
5. **표본 점검 추천** — 사람이 직접 점검할 규칙 3개를 추천한다(아래 절).

## 규칙 형식

~~~markdown
### BR-01
- 규칙: <한 문장. 입력 조건 → 동작. 코드가 하는 일 그대로>
- 근거: `<파일>:<시작줄>-<끝줄>`[, `<파일>:<줄>` ...]
- 근거 코드:
  ```php
  <규칙을 받치는 줄을 그대로 인용>   // <파일>:<줄>
  ```
- 확신도: 확실 (실행 확인) | 높음 (코드 읽기) | 낮음 (추정 — 이유)
- 비고: <주석-코드 불일치, 중복 구현, 미확인 사항, 관련 규칙 ID>
~~~

- ID 는 `BR-01` 부터 연번. 실행하지 않은 규칙은 "확실"로 쓰지 않는다.
- 줄번호는 저장 직전에 파일을 다시 열어 맞는지 확인한다.

## 하지 말 것 (docs/item-bank 검증 이력에서 실제로 틀렸던 유형)

- **주석 · 경고 문구를 동작으로 옮겨 적지 않는다.** 난이도 `3abc` 를 주석 "(대개 0건)"대로 0건이라 적었지만, PHP `(int)'3abc'` 는 3 이라 난이도 3 문항이 조회됐다(BR-08). 형변환 · 기본값이 끼면 경계값(`3abc` · `3.5` · `03` · `abc`)을 하나씩 따져 결과를 적는다.
- **코드 밖에서 결정되는 동작을 코드만 보고 단정하지 않는다.** "입력값 그대로 조회"라서 대소문자를 구분한다고 적었지만, 컬럼 콜레이션 `utf8mb4_unicode_ci` 때문에 `m5-1` 과 `M5-1` 결과가 같았다(BR-09 · BR-11). 문자열 비교 규칙에는 스키마의 콜레이션을 근거로 함께 적는다.
- **뷰 · 프로시저 뒤의 조건을 "참고" · "미확인"으로 넘기지 않는다.** 노출 조건(`status = 'A'`)이 뷰 `v_item_public` 정의에 있는데 추적하지 않아 규칙이 비어 있었다(BR-01 · BR-02). SQL 이 뷰를 읽으면 뷰 정의 줄까지 근거에 넣는다.
- **근거 줄 범위를 규칙보다 좁게 잡지 않는다.** 인용이 규칙 문장 전체를 받치지 못해 범위를 넓혀야 했다(BR-01 `:521-522` · `:526` 추가, BR-08 `:223-229`).
- 존재하지 않는 함수 · 파일 · 테이블을 쓰지 않는다. 이름은 grep 으로 확인한 것만 쓴다.
- 호출 방향을 뒤집지 않는다(호출하는 쪽 → 불리는 쪽). 방향은 호출 코드 줄을 근거로 적는다.
- 코드에 없는 규칙(업무상 그럴 법한 검증 · 권한 · 상태 전이)을 만들어 넣지 않는다. 없으면 "기능 없음"으로 적는다.
- 쓰기 요청(POST · INSERT · UPDATE)을 실행하지 않는다. DB 조회는 `readonly` 계정으로만 한다.

## 표본 점검 추천 (마지막 단계)

`BUSINESS-RULES.md` 저장 후, 사람이 코드 · 실행으로 직접 확인할 규칙 3개를 표로 추천한다.

| 순번 | 규칙 ID | 고른 이유 | 확인 방법(열어 볼 파일:줄 또는 요청 예시) |
|---|---|---|---|

- 1개는 **가장 그럴듯한 규칙**(읽기엔 당연해 보여 아무도 다시 보지 않을 규칙)을 넣는다. 그럴듯해서 틀려도 걸러지지 않기 때문이다.
- 나머지 2개는 확신도가 낮거나, 주석-코드 불일치 · 형변환 · 콜레이션 · 뷰처럼 위 "하지 말 것" 유형에 걸리는 규칙에서 고른다.
- 점검 결과로 규칙이 바뀌면 `BUSINESS-RULES.md` 맨 아래 "검증 이력" 표(날짜 · 규칙 · 바뀐 내용 · 방법)에 남긴다.
