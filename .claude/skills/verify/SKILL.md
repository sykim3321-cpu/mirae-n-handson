# 검증

검증 대상: $ARGUMENTS

- 위가 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.
- 이 Skill 은 **리뷰 세션**의 절차다. 코드를 고치기 시작하면(tester 가 추가하는 테스트 파일은 예외) 그 순간 "만든 쪽"이 되므로, 판정과 수정 방향만 보고한다.
- 절차의 근거는 저장소 루트의 `templates/verification-loop.md`, 판정 항목은 저장소 루트의 `templates/approval-checklist.md` 다. 경로는 모두 저장소 루트 기준이다.
- reviewer 또는 tester Sub-agent 가 없는 환경에서는 3 · 4단계를 위임하지 않고 아래 기준대로 직접 수행한다.

## 1. 요청 범위 확인

- 무엇을 요청했는지 한 문장으로 확인한다(대화, PR 설명, 커밋 메시지).
- 요청 범위가 주어지지 않았으면 **판정하지 말고 먼저 질문한다.** 답을 받기 전에는 2단계 이후로 넘어가지 않는다.

## 2. 변경 파일 목록과 diff 읽기

- 목록을 먼저 본다: git 범위면 `git diff --stat <범위>`, patch 파일이면 `git apply --stat <파일>`.
- 그다음 파일마다 diff 를 읽는다. 이슈의 근거로 댈 줄번호는 이 단계에서 확인한다.
- 변경 파일을 `modern/api` · `modern/web` · `characterization` · 그 밖으로 나눠 둔다. 4단계에서 실행할 테스트가 이것으로 정해진다.

## 3. 체크리스트 대조

- 직접 대조하지 않고 **reviewer Sub-agent 에 위임한다.** 1단계의 요청 범위 문장과 비교 범위(검증 대상 git 범위 · patch 파일 · 경로)를 그대로 넘기고, 아래 기준으로 대조하게 한다.
- 저장소 루트의 `templates/approval-checklist.md` 를 읽는다. 항목을 여기에 옮겨 적지 말고 그 파일을 기준으로 삼는다.
- 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
- 컨벤션 항목은 저장소 루트의 `CLAUDE.md` 와 대조한다. `convention-check` Skill 이 있으면 그 결과를 쓴다.
- 심각도(치명 / 경고 / 제안)는 체크리스트의 심각도 정의를 따른다.

## 4. 테스트 실행

직접 실행하지 않고 **tester Sub-agent 에 위임한다.** 2단계의 폴더 분류와 아래 기준을 넘긴다.

- 새 로직에 테스트가 없으면 tester 가 테스트 파일을 추가하게 한다.
- 실행 결과(실행 명령, 통과 · 실패 수, 실패한 테스트 이름, 추가한 테스트 파일 목록)를 돌려받는다.

변경된 폴더의 테스트만 실행한다.

| 변경된 폴더 | 실행 위치 | 명령 |
|---|---|---|
| `modern/api` | `modern/api` | `./gradlew test` |
| `modern/web` | `modern/web` | `npm test` |
| 이관 코드 | `characterization` | `npm test` (레거시 대상) 와 `TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 이관 코드는 `legacy/` 의 기능을 `modern/` 으로 옮긴 변경이다(요청 문장이 이관 · 리팩토링이거나 `characterization/lib/target.mjs` 가 바뀐 경우). 이때는 `modern/api` 테스트와 characterization 테스트를 둘 다 실행한다.

- **사용량 절약:** 결과는 통과 · 실패 수와 실패한 테스트 이름만 남긴다. 전체 로그를 대화에 싣지 않는다. 필요하면 출력을 파일로 돌리고 요약 줄만 읽는다.
- 실행할 수 없었으면(서버 꺼짐, 의존성 미설치, compose 미기동) 그 사실과 막힌 명령을 적고 사람에게 기동을 요청한다. 이 경우 "테스트 통과"는 미충족이다.

## 5. 승인 기준 판정

- 3단계 reviewer 보고와 4단계 tester 보고를 모두 받은 뒤, **메인 세션이** 네 기준을 모두 최종 판정한다.
- reviewer 와 tester 의 보고가 엇갈리면 엇갈린 지점을 그대로 적고 사람에게 묻는다. 답을 받기 전에는 판정하지 않는다.
- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다.
- **모두 충족이면 승인, 하나라도 미충족이면 반려.**
- 이슈가 0건이면 경고 · 제안 수준까지 한 번 더 본다. 0건은 결과일 수도, 안 본 것일 수도 있다.

## 6. 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | `경로/파일:줄번호` | … | … |

확인 필요
- (근거 줄번호를 댈 수 없는 지적, 사람이 확인해야 할 것)
```

- 이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향을 이 순서로 모두 채운다.
- 이슈가 없으면 표 대신 "이슈 없음"이라고 쓴다.

## 7. 하지 말 것

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 보고만 한다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 요청 범위를 모르는 상태에서 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.
